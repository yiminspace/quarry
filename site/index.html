Why Quarry

Agents need different guarantees than humans

DBeaver, TablePlus, pgAdmin — great tools, all designed for a person clicking. But more and more queries are run by AI agents, in skills, scripts, and CI. An agent can't "be careful". The tool has to be.

{} Results a machine can parse

GUI/MCP/Rust return {columns, rows, rowCount, truncated, elapsedMs, engine, sql}; CLI JSON returns row arrays — a stable, structured contract. No screen-scraping, no prose parsing.

▣ Rails that live in the kernel

Query entry points share read-only defaults and row caps. Write authorization is explicit: CLI and MCP add prod confirmation; Rust callers supply their own authorization. The GUI query interface stays read-only.

± Deterministic error contract

CLI query exit codes distinguish success, connection/execution failures and safety blocks. Parameter and command-specific errors have their own meanings; GUI/MCP/Rust expose structured errors. See the contract below.

We didn't bolt a chatbot onto a database GUI.
Your agent already is one — Quarry gives it a safe socket into your data.

The human face

And a real workbench for you

qy gui opens the bundled web workbench with grouped connections, schema browsing, SQL tabs, completion, EXPLAIN and searchable history. Inspect JSON and Redis keys, export CSV or JSON, and switch between light and dark themes in English or Chinese. In pure local mode, drafts and bounded result snapshots stay in browser storage.

✦ A SQL assistant beside the editor

Explain, generate or revise SQL with table metadata as context. A proposal can update the editor, and you can restore the previous SQL. Running a query remains a separate action.

▣ Keep control of your drafts

Opening a table preserves hand-written SQL. Connections explicitly marked as production start with Auto-run off; enabling it is a deliberate choice for that target.

⇄ Results follow the active tab

The grid and exports use the current tab's result. Overlapping requests keep the newest result; an older response cannot replace it. Sort, page, inspect and cancel without losing the target.

Architecture

One core, many faces

Connection management, query execution, schema introspection, and safety rails live in one importable kernel. Everything else is a thin shell. Shared fixes benefit the query interfaces; each interface defines its own authorization and error presentation.

Hosted workbench · one Docker image

Your IAM, your databases, the same workbench

Run the official Docker image with one configuration file for the GUI, sign-in, read-only API and query execution. Choose the built-in administrator or your platform's identity provider.

▣ Host-controlled read-only access

Expose only registered resources. Every remote query, metadata operation, cancellation and schema export checks live IAM permission and resource access. Database credentials stay on the server.

⌁ Open the hosted workbench in a browser

Sign in to query authorized server connections. Drafts and SQL history stay in account-scoped browser storage. Query results stay on the open page. A cached workbench can reopen for editing offline.

⇄ Combine local and hosted connections

With federation-enabled builds, sign in with ylab auth login and open ylab db gui to register your authorized catalog. qy gui and the CLI can then browse those connections alongside Quarry workspaces. Local queries run on your computer and cloud queries go through YLab. The two workbench launchers share local SQLite records for the same configuration. Cloud drafts and history are scoped to the signed-in account, and cloud query results stay in the current session.

▤ Deploy a versioned image

The image includes the compiled web assets and query service. Configure connections, reader grants and sign-in, then deploy a tested image. Upgrade the hosted workbench by deploying a newer image.

Remote queries send SQL to your host; the assistant sends required context to the configured model gateway. Their retention follows host policy. Hosted shared SQL, cloud personal history and cross-device sync are not included.

Safety rails

Read-only by default. Escalation is explicit and graduated.

CLI writes require --write; production targets also require confirmation or --yes. MCP writes need server and per-call opt-in, plus confirm_prod for production. Rust callers supply explicit write authorization; GUI and hosted queries are read-only. Read queries without an outer LIMIT default to 500 rows; --max-rows 0 disables the cap. Utility/locking queries are not rewritten; Redis caps after receipt. Production protection follows the connection's explicit classification, not its environment name.

Workspace as code

Your connections and queries are files, not clicks

In standalone mode, a workspace is a directory: connections.toml plus named queries as plain .sql files with metadata headers. Version query files and credential-free configuration templates in your repo; keep real connection credentials local. Quarry aggregates multiple workspaces into one view. These local query files are separate from hosted personal history; a hosted shared-query library is not implemented.

connections.toml
[shop_dev]
url    = "postgresql://user:password@dev.example.com:5432/shop"
db     = "shop"
env    = "dev"

[shop_prod]
url    = "postgresql://user:password@prod.example.com:5432/shop"
db     = "shop"
env    = "prod"
production = true

[internal_db]
url      = "postgresql://user:password@127.0.0.1:5432/appdb"
ssh_host = "bastion.example.com"  # auto tunnel
queries/shop/recent_orders.sql
-- @name: recent_orders
-- @db: shop
-- @desc: Latest orders with customer names
-- @param: days (int, default=7)
SELECT o.id, c.name, o.amount, o.status
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.created_at > now() - make_interval(days => :days)
ORDER BY o.created_at DESC;

Same logical database across dev / staging / prod folds into an env-set — one saved query runs against any environment: qy run recent_orders --env prod.

Engines & footprint

Nearly zero dependencies

A native Rust executable with embedded GUI and database drivers. Install on macOS or Linux on arm64 and x86_64. The installer-managed binary updates with qy update. SSH, Docker and schema sync use system tools when needed.

PostgreSQL · native SQLx MySQL · native SQLx Redis · native redis-rs Neptune · experimental openCypher SSH tunnels · system ssh SQLite · bundled DuckDB · planned

Neptune is experimental: the openCypher endpoint integration is available, but real AWS/IAM behavior has not completed release acceptance. The local empty endpoint does not execute or store graph data. See the support and interface contract for tested environments, persistence limits and error codes.

⌁ A real library, importable

Embed the execution kernel with quarry-service::QuarryService, the CLI with quarry-cli::run_from, or the localhost workbench with quarry-cli::run_gui_from. The embedding application builds and ships its own binary.

▣ Choose where it runs

Quarry binds the native GUI to localhost. Local workspaces stay available offline, and registered cloud access uses your platform account. Model requests use your configured provider. Disable GitHub release checks with QUARRY_UPDATE_CHECK=0.
